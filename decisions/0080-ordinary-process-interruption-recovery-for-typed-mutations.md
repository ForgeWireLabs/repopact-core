# 0080: Ordinary process-interruption recovery for typed mutations

## Context and authority

WI084 is the integrated mutation foundation at `1223cab5562f2f4c5a77acb5e6ce8d033aa5a0cb` (tree `685528fcfc59601b6c32470d3cd07a43dfebf8b1`). Its typed ordinary create, edit, and transition operations validate the content-addressed plan, capture checked preimages, apply a finite write set, perform live post-validation, and roll back in-process failures. A terminated process loses its in-memory undo records, so the repository may be left between writes without a durable recovery decision. The archival PR #15 implementation contains useful transaction-store patterns, but its root rollback and other older recovery assumptions are not authoritative after WI084.

The repository operator authorized this bounded implementation in the current execution request citing [PR #15 coordinator authorization](https://github.com/ForgeWireLabs/repopact-core/pull/15#issuecomment-7230402419). The linked comment is authored by `github:JeremyShows` and records that the operator authorized proceeding after WI084 integration. This acceptance is limited to WI085 and does not grant frozen-surface, merge, hosted CI/CD, or release approval.

## Decision

1. Add persistent state only for supported ordinary typed `create_work_item`, `edit_work_item`, and `transition_work_item` mutations. Keep proposal creation/amendment semantics and artifacts separate. Do not include decision/policy editing, takeover, generic filesystem requests, power-loss recovery, or malicious same-principal protection.
2. Store ordinary-v1 state beneath the exact working root at `work/.repopact-transactions/ordinary-v1`. Use one stable lock file there for ordinary mutation and proposal admission/commit so operations on the same working root contend regardless of `TEMP`; linked worktrees have distinct anchors. Bind every record to canonical working-root path and native directory identity. Reject cloned, copied, moved, or recreated roots whose identity does not match.
3. Use bounded versioned journals for nonterminal mutations and compact terminal receipts. Keep the request/idempotency key distinct from the plan token and payload digest. Bind the key to the canonical typed intent, repository/worktree identity, and original authorized plan. The caller supplies a key for API use; the CLI prints or flushes a stable key before its first write. A read-only status operation can discover a generated key after an interrupted response. Same key and same intent returns the durable terminal result without replaying; changed intent conflicts. Rejected and rolled-back keys remain terminal. A missing receipt means outcome unknown, never “nothing happened.” Do not silently retry after transport loss.
4. Before touching governed paths, atomically publish and verify a complete prepared journal containing the exact WI084 preimages, ordered operation list, deterministic projected after-state, sequence, bounds, and integrity digest. A prepared record is the authorization for the transaction’s exact write set, not a license to replan. Keep preimages until terminal receipt publication. Existing in-process rollback follows the same path ownership and captured-state rules.
5. Record the state transition and operation sequence before/after each governed write. A terminal committed receipt is published only after all operations, independent live post-validation, and durable receipt publication succeed. Terminal receipts are bounded and compact. Capacity exhaustion, unsafe storage permissions, or journal publication failure blocks before the first live write. Never silently evict or delete transaction records to make room.
6. Provide explicit read-only status and explicit recovery under the shared lock. Planning, preview, status, and validation never create, clean, or roll back transaction state. Ordinary apply and proposal operations reject pending or ambiguous ordinary recovery. Do not automatically recover during an unrelated request; successful recovery does not authorize applying a stale plan.
7. Recovery verifies root identity, record version/phase/sequence/key/intent/operation paths, bounded sizes, full path-chain containment, single-link regular files, and all integrity digests. Compare each operation path against its exact captured before-state and deterministic after-state. If all paths are already before-state, record rolled-back without rewriting. Otherwise reverse only states proven to be this operation’s after-state, using WI084 ownership checks. Unknown, mixed, externally edited, corrupt, missing, linked, escaped, or root-mismatched state is preserved and reported recovery-required; do not restore an entire root or speculate forward. Repeated recovery is idempotent and must not make further changes when ownership cannot be proved.
8. Remove only exact known artifacts owned by a terminal transaction after the terminal record is safe. Preserve unknown artifacts and corrupt evidence. Never recursively clean a prefix or remove ordinary state from proposal cleanup. Do not expand atomic replacement behavior to claim ACL/metadata preservation unless a separately reviewed implementation is required.
9. Keep the direct writer inventory narrow. The typed mutation API is the ordinary writer covered here. The engine’s `dashboard.write` is an actual overlapping writer because it writes `audits/reports/dashboard.md`, which is in ordinary mutation write sets; route it through the shared lock and refuse it while recovery is pending. Proposal commit already shares the mutation lock and must also check pending ordinary state. Graph output under `build/` and Python evidence-run creation are separate direct writers with disjoint governed targets; they do not join this transaction. Do not claim a universal repository lock. Document that operators must pause uncoordinated external writers to the affected paths during explicit recovery.
10. Maintain explicit exclusion of ordinary-v1 state from candidate snapshots and copy/measurement tooling; do not broaden existing proposal-stage cleanup. Add API/CLI status and recovery through the existing typed mutation/engine admission path, with explicit outcome states. Preserve compatibility defaults only when they cannot bypass pending-recovery admission.

## Alternatives considered

- **Rely on in-process undo and tell users to inspect partial state.** Rejected because process termination discards undo state and leaves no authoritative outcome.
- **Reuse the archival PR #15 recovery behavior wholesale.** Rejected because blind root restore, lossy path identity, overbroad cleanup, and stale authorization semantics conflict with WI084 containment, preimage, and concurrent-user guarantees.
- **Automatically complete or roll back on every repository request.** Rejected because unrelated reads/writes would acquire hidden mutation behavior, stale plans could be revived, and unknown external edits could be overwritten.
- **Use a global writer framework, external database, or per-user temporary state.** Rejected as unnecessary scope and because the repository-local working-root anchor gives the required same-root coordination and explicit ownership boundary.
- **Claim power-loss or hostile same-principal protection.** Rejected because this batch proves process interruption for a trusted local principal, not filesystem/device durability or a security boundary against the same user.

## Consequences and limits

Ordinary supported mutations can report an unknown response without losing their exact authorized preimage and after-state. Recovery is explicit, bounded, idempotent, and conservative; ambiguous state blocks instead of overwriting uncertain user data. Proposal state remains distinct while sharing admission exclusion. The repository-local anchor adds bounded disk usage and a lock/journal write cost per mutation. The implementation and tests must measure that overhead using existing fixtures. This decision does not make out-of-band repository writers participate in the lock and does not promise recovery from power loss, storage rollback, or same-principal tampering.
